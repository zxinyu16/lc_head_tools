# 小程序内 PDF / 图片识别可行性评估

- 日期：2026-09-26
- 结论：**当前条件下不实施小程序内 OCR，维持“粘贴文本 + 人工核对”链路；待正式 AppID 与 CloudBase 恢复后，优先采用“CloudBase 云函数 + 腾讯云 OCR”方案。**

## 约束条件

1. 尚无正式小程序 AppID，`project.config.json` 使用 `touristappid` 本地调试。
2. 用户明确暂缓 CloudBase 连接与云环境创建。
3. 信用证含客户商业资料，真实样本仅允许在本机 `.local/` 使用；任何把原文发送到端外的识别服务，都需要用户先做数据出端合规确认。
4. `scripts/ocr-pdf.py`、`scripts/ocr-image.swift` 是 macOS 开发工具，不属于小程序功能，不能作为小程序识别能力的依据。

## 候选方案对比

| 方案 | 识别位置 | 前置条件 | 数据出端 | 当前可行性 |
|---|---|---|---|---|
| A. CloudBase 云函数 + 腾讯云 OCR | 云端 | 正式 AppID、云环境、费用预算 | 是（腾讯系） | ❌ 云端已暂缓 |
| B. 微信官方 OCR 插件（插件市场） | 云端 | 正式 AppID，部分插件要求非个人主体并单独申请 | 是 | ❌ 无 AppID |
| C. 第三方 OCR API（wx.request 直连） | 云端 | 正式 AppID、request 合法域名、密钥需服务端中转 | 是（第三方，合规风险最高） | ❌ 无 AppID、无中转服务端 |
| D. 端上识别（Tesseract.js / WASM） | 手机本地 | 无 AppID 也可尝试 | 否 | ⚠️ 技术验证后可排除，见下 |
| E. 维持文本粘贴 + 本机 OCR 辅助 | 本机/手动 | 无 | 否 | ✅ 当前方案 |

### 方案 D 的技术判断

- 主包 2 MB 限制下需分包加载数 MB 的中英文 traineddata，首次加载体验差。
- 小程序 WASM 支持有限，扫描件识别耗时以十秒计，且 SWIFT 场次混排（`:46A:`、换行缩进、德文/英文混排）识别错误率高，与“识别结果必须人工核对”的定位叠加后收益很低。
- 扫描版 PDF 还需先在端上渲染成图；pdf.js 在小程序环境兼容性差、体积大。
- 结论：即使投入开发，也达不到“减少人工核对”的目的，不建议投入。

## 推荐路线

**短期（当前阶段）**

- 维持方案 E：开发机在 macOS 上用 `scripts/ocr-pdf.py` 本机 OCR 后粘贴进小程序；手机端手动复制文字版信用证粘贴。识别候选全部走人工核对，已在编辑器页面实现。
- 继续用脱敏样本打磨 `miniprogram/lib/lc-text.js` 的保守解析规则（46/47 场、场次说明下一行为值的排版），这部分规则未来可直接复用在云端识别之后。

**中期（取得正式 AppID 且用户恢复 CloudBase 后）**

- 实施方案 A：小程序上传文件到云存储（临时目录）→ 云函数调腾讯云 OCR（通用印刷体识别）→ 识别文本回传 → 复用 `lc-text.js` 生成候选 → 人工核对后写入业务。
- 云函数内不持久保存原文；识别完成后删除临时文件；保存期限与删除策略在接入前由用户确认（PRD 第 11 节待决策项）。
- 同步评估方案 B（微信官方 OCR 插件）作为免自建云函数的替代，取决于届时主体类型与插件申请条件。

**决策前提清单（接入任何云端识别前）**

1. 正式小程序 AppID 及主体类型确定。
2. 用户对信用证原文出端识别的合规确认。
3. CloudBase 环境与识别费用预算。
4. 文件保存期限与删除策略。

## 验收口径提醒

- 小程序“文件上传”目前仅供本地查看；在任何云端识别落地前，对外表述应保持“尚未支持小程序内 OCR”。
- 本机 OCR 的开发验证结果不能写成“小程序已支持 PDF 自动识别”。
